## Goal and requirements

Produce a faithful native PC recompilation of the Nintendo 64 version of **International Superstar Soccer 2000**, starting with the user's existing USA English/Spanish ROM. Preserve the original football simulation, rules, modes, audio, language selection, and save behavior. The explicitly requested enhancements are:

| Requirement | Intended behavior | Acceptance evidence |
| --- | --- | --- |
| 16:9 | Wider 3D field of view, correct projection, readable HUD and menus | Same scene at 4:3 and 16:9; circular elements retain their shape; newly visible sidelines render correctly |
| Up to 4K | Configurable internal rendering through 3840 × 2160 | Renderer target dimensions and visible output from the actual build |
| 120 fps with interpolation | Interpolated presentation independent of the original simulation cadence | Distinct intermediate frames, measured presentation rate, matching simulation ticks and match clock for identical input |
| Expansion Pak | Guest-visible 8 MiB RDRAM, correct memory reporting and game detection | Guest-reported size, allocation/range checks, observed game behavior with expanded memory |
| Controller rumble | Original motor requests routed to the appropriate physical controller | Logged guest requests plus physical checks for each available controller family |

Assumptions carried over from the user's other native N64 projects: Linux first, Windows after the baseline works; CMake and C++20 host; four logical N64 controller ports; action-based remapping; Xbox, PlayStation and Nintendo prompts tied to the active device; English project documentation. These are design defaults, not measurements or claims about existing ISS2000 support.

Keep the original assets at their original fidelity unless a separate enhancement is requested. Rendering at 4K does not create replacement high-resolution textures. The current scope does not include online play, new football AI, new teams, or a gameplay rewrite.

## 2. Static boot findings

Rabbitizer disassembled the canonical ROM directly in memory using the existing analysis environment. The initial mapping is ROM `0x1000` to guest `0x80000400`.

| Observation | Evidence and interpretation |
| --- | --- |
| Initial BSS clear | Entry instructions clear from `0x800A0600` for `0x0010F780` bytes, ending at `0x801AFD80` exclusive |
| Initial stack | The entry sequence establishes `sp = 0x800CEC50` |
| Boot transfer | An indirect jump at `0x80000438` transfers to `0x800007B8` |
| Early thread setup | Calls at `0x800007F4` and `0x800007FC` target `0x8005DAD0` and `0x8005DC90`; arguments resemble thread creation and start. Names remain hypotheses until matched against SDK code |
| F3DEX marker | ROM `0x9D618` contains `RSP Gfx ucode F3DEX fifo 2.06` |
| F3DLX.Rej marker | ROM `0x9DA38` contains `RSP Gfx ucode F3DLX.Rej fifo 2.06` |
| Save-related strings | `SRAM INIT` and SRAM debug strings occur near ROM `0xA03AA..0xA0430`. These are leads, not proof of the active save device |

Microcode strings identify candidates for renderer compatibility checks. They do not establish which modes use each variant. The BSS boundary does not establish the text section boundary. Do not classify every word before BSS as executable or treat raw `jal` bit patterns in that range as a validated function map.

No dynamic trace, native boot, save/load test, Expansion Pak detection test, physical rumble test, or interpolation test has been performed yet.

## 3. Architecture and alternatives

**Recommended: static MIPS recompilation with N64Recomp + N64ModernRuntime + RT64.** This matches the reusable foundation verified in the user's Tetrisphere, ClayFighter 64 and Power Dozer projects. Generate native C functions from recovered code boundaries and verified metadata; retain the original simulation; replace console services through runtime interfaces; render the original graphics tasks through RT64. Recompile or otherwise explicitly handle identified audio RSP microcode after tracing real task dispatch.

Alternative A is a full matching decompilation before porting. It offers source-level control but substantially expands the prerequisite work before the first playable build. Alternative B is an emulator launcher with graphics enhancements. It can serve as the comparison reference, but does not satisfy the requested native recompilation. Neither alternative is the proposed implementation.

The native components are:

1. **ROM importer:** normalization, revision checking, local asset access and import provenance.
2. **Binary metadata and recompiler:** code/data separation, symbols, jump tables, overlay identity, deterministic generated output.
3. **Guest runtime adapter:** libultra dispatch, threads, queues, timers, DMA, RSP tasks, VI timing and save storage.
4. **Renderer adapter:** RT64 task submission, projection patches, presentation pacing and interpolation boundaries.
5. **Input/accessory adapter:** logical actions, four guest ports, Controller Pak storage where needed, Rumble Pak behavior, device routing and hot-plug cleanup.
6. **Platform layer:** window, audio device, portable settings and data paths, Linux and Windows packaging.

The game continues to read its own ROM assets. Generated output and private inputs are reproducible build products, not handwritten substitute gameplay.

## 5. Feature contracts

### Expansion Pak

Allocate 8 MiB of guest RDRAM and report the same size consistently through boot variables, memory-query functions, address validation and graphics/audio task memory. Bounds checks remain active at 8 MiB. A diagnostic 4 MiB configuration can be used to compare the game's detection path; the requested enhanced profile uses 8 MiB.

Do not infer that allocating 8 MiB alone enables an original high-resolution mode. Observe the actual game branch and option behavior first. Host rendering resolution remains independent of the game's own VI/framebuffer mode. Reserve no arbitrary game memory for host features.

### Rumble and controller accessories

Identify and bind the actual motor routines used by the game. Route each guest channel to its assigned host gamepad. Support start/stop, a master enable option and controller capability checks. Stop active motors on pause where appropriate, disconnection, loss of focus, game reset and application shutdown. A controller without a motor must continue to work.

Controller Pak and Rumble Pak are distinct guest accessories sharing a port. Preserve the game's accessory detection and switching expectations instead of blindly reporting both as the same device. Save and accessory semantics are to be measured before selecting the save backend.

### Widescreen and resolution

Preserve a 4:3 comparison profile. Apply an aspect-correct perspective to gameplay; verify culling separately so widening the projection does not reveal missing players or scenery. Keep text, scoreboard, radar, menus and 2D sprites proportioned correctly. Review replays, cutscenes and transitions independently. Render at 1080p, 1440p or 2160p through renderer configuration rather than changing gameplay timing.

### Interpolation to 120 fps

Measure the native simulation and VI cadences first. Retain them. Interpolate rendering between actual simulation states, using stable player/ball/camera matching and explicit reset boundaries for cuts, substitutions, replays, goals and menus. Never interpolate through a teleport, scene replacement or invalid object pairing.

Validate camera movement, animated players, ball trajectories and the HUD separately. A 120 Hz window or repeated frames does not pass interpolation acceptance. Collect actual presentation timestamps and distinct fractional-frame evidence. Compare match clock and simulation state at identical guest ticks for recorded input. Retain an original-presentation profile for diagnosis. Performance at 4K/120 depends on hardware and is not promised before measurement.

## 8. Verification and failure handling

Input checks must reject truncated images, unsupported canonical hashes and ambiguous ZIP contents. Check supported byte orders against the same canonical digest without changing the original file.

Mapping acceptance requires real code boundaries and traced dispatch. Unknown indirect calls, unrecognized RSP tasks and unmapped guest OS calls must produce actionable diagnostic failures; silent success stubs are not acceptable substitutes.

Baseline evidence must include title-to-match navigation, controller input, audio progression, pause/resume, match progression, save reload and clean shutdown. Enhanced-mode evidence must include scene transitions and identical-input timing comparisons, not just menu screenshots or an FPS counter. Physical rumble requires a physical controller test; a mock callback only verifies routing.

Capture actual build identity, dependency revisions, ROM digest, rendering profile and test environment with each run. Keep original ROMs, original assets, captured game imagery/audio, saves and generated game code out of public source and artifact uploads. Package the importer and original project work with accurate upstream attribution and applicable licenses.
